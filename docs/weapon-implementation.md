# 무기 구현 작업 순서

이 문서는 지금까지 등록된 무기 29개(등방울꽃의 애가·붉은 달의 형상·나른한 새해·초월의 열쇠 …)가
실제로 거쳐 온 순서를 그대로 옮긴 것이다. 새 무기를 넣을 때는 이 순서대로 진행한다.

캐릭터 쪽과 겹치는 규칙(Phase 정의, 지연 기여, 자기 참조 순환)은
[`docs/character-implementation.md`](character-implementation.md)에 있다. 캐릭터도 같은 꼴의
스펙 파일과 생성기(`tools/new_character.py`)를 쓴다 — 절차의 모양이 둘이 같다. 여기서는
**무기라서 다른 것**만 적는다. 무기가 캐릭터와 다른 점은 셋이다.

- 기본 공격력·부옵션을 **선언하지 않는다.** 성급·티어·레벨에서 유도된다.
- 훅이 셋이다 — `add_hits`(Phase 1), `apply_passive`(Phase 3), `apply_passive_dependent`(Phase 5).
- 착용자가 있다. 효과의 대상이 착용자인지 파티인지 제3자인지가 매번 갈린다.

---

## 0. 이 작업이 건드리는 파일

| 파일 | 언제 |
|---|---|
| `_specs/weapons/<모듈>.txt` | 항상 — 자료 원문 |
| `gidc/content/weapons/<종류>/rarity_<성급>/<모듈>.py` | 항상 — 본체 |
| `gidc/content/weapons/<종류>/__init__.py` | 항상 — `from .rarity_N.<모듈> import <Class>` |
| `gidc/content/weapons/__init__.py` | 항상 — import 묶음 **과** `WEAPON_REGISTRY` (**두 곳**) |
| `web/engine.zip` | 항상 — `python tools/sync_web.py`로 재생성 |
| `gidc/core/profile.py` | 새 `SkillHit` 필드가 필요할 때만 |
| `gidc/core/explain.py` | 새 필드를 explain 화면에 태울 때만 |

`gidc/core/party.py`는 **줄 수를 늘리지 않는다.** 질문 ID가 (호출 지점 줄 번호, 반복 횟수)라
위쪽에 한 줄만 보태도 아래 `ask_*`들의 ID가 밀려 이미 저장된 웹 답변이 통째로 떨어진다.
고칠 일이 있으면 줄 수 불변 교체 + 헬퍼는 다른 파일(또는 맨 아래)에 둔다.

등록은 **세 곳**이다(종류별 `__init__` 1 + 최상위 `__init__`의 import와 레지스트리 2).
빠지면 `ImportError`로 죽거나 `make_weapon`이 「미등록 무기」로 거절한다.

## 1단계 — 자료를 스펙 파일로 옮긴다

사용자가 준 원문을 손으로 요약하지 말고 `_specs/weapons/<모듈>.txt`에 그대로 넣는다.
이 파일이 나중에 기댓값의 출처가 된다 — 검증할 때 숫자를 다시 타이핑하지 않기 위해서다.

```
이름: 초월의 열쇠
영문: A Teaspoon of Transcendence
종류: CLAYMORE
성급: 5
기본공격력: 674
부옵션: CRIT_DMG 44.1
패시브: 하얀 여왕의 승급

수치:
  ATK_PCT     = 28/35/42/49/56 %
  STELLAR_DMG = 16/20/24/28/32 %

설명:
- 공격력이 28/35/42/49/56% 증가한다.
- ...
```

형식 규칙 — `tools/new_weapon.py`가 강제한다.

- **기본 공격력과 부옵션은 Lv.90 값**이다. 게임 표기가 `48 ~ 674`, `9.6% ~ 44.1%`면
  오른쪽 값을 적는다.
- `수치:` 줄은 정확히 `NAME = a/b/c/d/e %` 꼴이다. 뒤에 괄호 주석을 달면 파싱이 실패한다.
  스택 상한 같은 부가 정보는 `설명:` 블록에 둔다.
- 정련 값은 **5개**여야 하고 단조여야 한다. 오르내림이 섞이면 옮겨 적다 틀린 것이다
  (페보니우스 계열의 발동 간격 12/10.5/9/7.5/6처럼 **내려가는** 수열은 정상이다).
- 숫자열은 `설명:` 원문에 **실제로 있어야** 한다. 배열만 고치고 설명을 안 고친 사고를
  여기서 잡는다.

## 2단계 — 티어 되찾기 (`--check`)

「티어」는 한 성급 안의 등급이고 기본 공격력·부옵션 등급을 겸한다. **게임 화면에 적혀 있지
않으므로** 화면에서 읽히는 두 값에서 각각 독립으로 되찾고 **둘이 일치하는지 대조한다.**

```bash
python tools/new_weapon.py _specs/weapons/<모듈>.txt --check
```

```
[초월의 열쇠]  양손검 · 5성 · Tier 3
  기본 공격력 674 → Tier 3 (표: 674.3)
  부옵션 CRIT_DMG 44.1 → Tier 3 (표: 44.1)
  _ATK_PCT = [0.28, 0.35, 0.42, 0.49, 0.56]
  _STELLAR_DMG = [0.16, 0.2, 0.24, 0.28, 0.32]
```

두 티어가 어긋나면 스크립트가 거절한다 — 둘 중 하나를 잘못 옮겼거나 Lv.90이 아닌 값을 넣은
것이다. 여기서 출력된 정련 배열이 그대로 클래스 상수가 된다.

---

## 3단계 — 뼈대 생성과 등록

`--check`를 뗀 같은 명령이 파일 생성과 등록 3곳을 한 번에 한다.

```bash
python tools/new_weapon.py _specs/weapons/<모듈>.txt
```

`apply_passive`는 `NotImplementedError`와 관용구 주석만 남는다 — **어느 훅에 어떤 필드로
넣을지는 스크립트가 판단하지 않는다.** 손으로 만들었다면 등록 세 곳을 직접 확인한다.

무기 클래스가 선언하는 것은 **성급·티어·부옵션 종류** 셋뿐이다. `542`나 `66.2` 같은 최종
숫자를 손에 들고 있으면 레벨을 바꿀 수 없고 틀려도 드러나지 않는다.

## 4단계 — 훅 고르는 기준

| 효과 | 훅 | 출력 |
|---|---|---|
| 무기가 **새 히트**를 만든다 (추가 타격) | `add_hits` (Phase 1) | `hits[이름] = SkillHit(...)` |
| 착용자 고정 스탯 (공격력%·치명타 피해·원소 마스터리) | `apply_passive` (Phase 3) | 코어 풀에 `hit.add(...)` |
| 스킬 타입별 피해 보너스 | `apply_passive` | 타입 → 필드 맵을 클래스 속성으로 |
| 파티 전원 고정 버프 | `apply_passive` | `hit.apply_unique_buff(...)` |
| 착용자 **최종 스탯**에 스케일 (방식 B) | `apply_passive_dependent` (Phase 5) | `flat_dmg_bonus` 등 **피해 풀만** |

### 추가 타격 (`add_hits`)

무기 패시브가 히트를 하나 더 만드는 경우다(천공 시리즈의 진공의 칼날). 규칙 셋.

- **Phase 1이어야 한다.** `apply_passive`(Phase 3)는 기초 스탯·무기 부옵션·성유물 옵션·
  세트 효과가 이미 실린 뒤라, 거기서 끼워 넣은 히트는 `atk_base`가 0인 채로 남아 아무것도
  곱하지 못한다. Phase 1에 넣어야 이후 모든 단계가 캐릭터 히트와 똑같이 훑어 준다.
- **`skill_type`은 `SkillType.WEAPON`이다.** 일반/강공격 명중으로 발동하더라도 그 자신은
  일반 공격이 아니다. 이 멤버는 `_SKILL_PREFIX`에 **일부러 빠져 있어** 스킬 타입별 피해
  보너스가 0으로 접힌다 — `NORMAL_ATK`으로 두면 날아오르는 유성 4세트 같은 것까지 잘못 받는다.
- **질문은 여기서 하지 않는다.** 종전대로 `apply_passive`에 모으고, 조건이 꺼져 있으면
  거기서 `hits.pop(이름, None)`으로 도로 뺀다. 계수 0으로 남기면 피해 0짜리 줄이 화면에
  남아 「발동했는데 0인가」로 읽힌다.

발사 횟수(긍지 8회, 마루 50%·2초 쿨)는 계수에 접지 않는다 — **히트 1개가 1발**이고 몇 발이
로테이션에 들어가는지는 유저가 정한다.

판단은 **수혜자**가 아니라 **무엇을 읽는가**로 한다.

- 스탯을 읽지 않는 고정값이면 파티 전원에게 뿌리더라도 Phase 3이다(드래곤 슬레이어 영웅담).
  코어 풀 출력을 Phase 5에 두면 정확성 가드에 걸린다.
- 최종 스탯을 읽어야 하면 Phase 5로 내리고, 값이 아니라 **읽는 함수**를 넘긴다
  (바위산을 맴도는 노래의 `lambda: source_hit.current_def() / 1000 * ...`). 값으로 넘기면
  뒤에 붙는 기여를 놓치는 순서 의존이 생긴다.
- 공격력→공격력처럼 자기 참조가 되는 변환은 `atk_flat_derived` + `convertible_atk()`로 끊는다.

**동명의 무기끼리는 중첩되지 않는다.** 파티 전원 또는 제3자에게 뿌리는 효과는 반드시
`apply_unique_buff` / `add_all_elemental_dmg_bonus_unique`로 제출한다 — 소스 키가 「동명」
판정이다. 착용자 자신에게만 붙는 효과는 그냥 `add`다.

**대상 범위를 문구에서 읽는다.**

- 「장착 캐릭터의 …」 → 착용자 히트만.
- 「파티 전원 …」 → 전원 + 비중첩.
- 「교체되어 등장한 캐릭터」·「현재 필드 위 캐릭터」 → **한 명**이다. `ask_choice`로 고르게
  하고(드래곤 슬레이어 영웅담), 후보에서 착용자를 뺄지도 문구가 정한다.

## 5단계 — 유저 입력 설계

질문은 **`apply_passive`(Phase 3) 안에서만** 한다. 지연 기여 함수 안에서 `ask_*`를 부르면
질문 집합이 흔들린다. Phase 5에서 쓸 답은 Phase 3에서 받아 `self._stacks`처럼 들고 간다.

무엇을 묻고 무엇을 유도할지는 「메커니즘을 함수로」 규칙을 따른다 — 파티 구성만으로 정해지는
것은 묻지 않고 유도하되, **로테이션이 정하는 것은 묻는다.**

- 강공격 명중 횟수, 「불빛」 획득 여부, 스킬/폭발 명중 여부 → 묻는다. 파티로 유도되지 않는다.
- 스택은 `ask_int(…, 0, MAX)` 하나로 받고 **문구에 무엇이 스택을 쌓는지 적는다**
  (`「초월」 스택 수 (강공격이 적에게 명중, 최대 3)`). 증가량도 적으면 화면에서 바로 읽힌다.
- 조건들이 **서로를 함의하면** `ask_choice` 하나로 단계를 고르게 한다(붉은 달의 형상).
  따로 물으면 「30% 이상인데 미보유」 같은 모순 입력이 생긴다.
- 조건들이 **독립이면** `ask_bool`을 나란히 세우고 켜진 만큼 합산한다(나른한 새해 — 트리거도
  지속 시간도 셋이 따로다).
- 주어가 없는 문구(「확산 반응 발동 후」)는 착용자로 좁히지 않는다. 뒤 줄들이 「장착 캐릭터의
  …」로 주어를 밝히는데 그 줄만 없다면, 파티 발동일 가능성을 닫지 않는다.
- 그 파티에서 효과가 성립하는지로 질문을 막지 않아도 되는 경우가 있다 — 읽는 히트가 아예
  없으면 답이 무엇이든 결과가 같다(초월의 열쇠의 별 반응). 막으려면 무기가 파티 판정을 한 벌
  더 들어야 한다.

## 6단계 — 「의도적 미구현」 블록

클래스 맨 아래에 주석 블록으로 **반드시** 남긴다. 무기 문구에는 히트 단가에 들어갈 자리가
없는 항이 거의 항상 섞여 있다.

- 지속 시간·재발동 쿨타임·스택 누적 속도 → 스택 수만 묻고 유지 여부는 유저가 판단한다.
- 원소 에너지 회복 → 로테이션 빈도를 정하는 값이지 피해 항이 아니다.
- 「대기 상태에서 카운트가 멈춘다」류의 지속 시간 보정.

적지 않으면 다음 사람이 「빠뜨린 것」인지 「뺀 것」인지 구별할 수 없다.

## 7단계 — 검증

### (1) 실제 파티에서 필드가 붙는지

`prompt.MappingSource`로 답을 주입해 `Party(...).build_profiles()`를 돌린다. 질문 ID는
호출 지점이라 한 번 돌려서 뽑아 쓴다.

```python
src = prompt.MappingSource({})
with prompt.using(src):
    hits = Party(wearer, other).build_profiles()
for q in src.asked:
    print(q.id, q.kind, q.display_prompt)
```

효과를 받을 히트가 실제로 있는 파티를 고른다 — 별 반응 무기면 산드로네 + 바람 캐릭터처럼.

### (2) 정련 1~5 전부 훑는다

값 하나를 확인하는 것으로는 인덱스 실수(`self.refinement`를 `-1` 없이 쓰는 등)가 안 잡힌다.
1~5를 돌려 배열과 정확히 일치하는지 본다. 스택이 있으면 1스택이 최대 스택의 정확한 분수인지도
같이 본다.

### (3) 켜기 전/후 비교 — 안 받아야 할 히트가 안 받는지

조건 off/on 두 번 돌려 **변한 히트와 안 변한 히트를 둘 다** 확인한다. 배율은 공식에서 유도해
대조한다 — 예를 들어 별·달 반응의 `reaction_bonus`는 `(1 + em_bonus + reaction_bonus)` 항에
들어가므로 0.96을 넣었다고 피해가 1.96배가 되지 않는다.

기댓값은 **손으로 타이핑하지 말고** 스펙 파일이나 표에서 유도해 비교한다.

### (4) 회귀 기준선 diff

```bash
python bench.py < _baseline/answers.txt > /tmp/out.txt 2>&1
```

```bash
diff _baseline/baseline.txt /tmp/out.txt
```

**신규 무기는 bench 파티가 끼고 있지 않으므로 diff가 비어야 정상이다.** 비어 있지 않다면
코어를 건드린 부분이 기존 계산을 바꾼 것이다. 의도한 변화인지 눈으로 확인하기 전에는
기준선을 덮어쓰지 않는다.

## 8단계 — 웹 반영

```bash
python tools/sync_web.py
```

검사 → `engine.zip` 번들 → `app.js` 캐시 버전 갱신을 한 번에 한다. 출력의 **무기 개수가 1
늘었는지** 확인한다 — 등록 누락이 여기서 드러난다.

## 9단계 — 커밋과 보고

커밋 범위: 스펙 파일 + 무기 파일 + 등록 3곳 + `web/engine.zip`.
제목은 `무기 추가 - <종류>/<이름>`.

본문과 보고에는 반드시 넣는다.

1. 코어를 건드렸는지 여부 (「코어 수정 없음」도 정보다)
2. **판단이 갈린 자리와 그 이유** — 왜 이 훅인지, 왜 이 질문 꼴인지, 비슷한 앞 무기와 무엇이
   달라 다르게 갔는지
3. 검증 결과 (정련 스윕·조건 on/off·기준선 diff)
4. **의도적으로 미구현한 항목**

## 부록 — 자주 하는 실수

- 등록 3곳 중 하나 누락 → `ImportError` 또는 「미등록 무기」 거절
- 스펙에 Lv.1 값을 적음 → 티어 역산이 어긋나 `--check`가 거절
